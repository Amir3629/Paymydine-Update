# PayMyDine platform language architecture

## Principle

PayMyDine treats **customer-menu language support** and **Admin language support** as separate capabilities.

This prevents a market from exposing a half-translated Admin just because its customer menu is available in another language.

## Customer-menu language pack

A customer-menu language consists of:

1. A locale definition in `App\Services\Platform\PlatformLanguageRegistry`.
2. A complete `UiLabels` dictionary in Frontend V2 `src/lib/i18n.ts`.
3. Market eligibility in `CountryPlatformProfileRegistry`.
4. Framework compatibility bridges under `language/<locale>/` when that locale needs to be recognized by the PHP platform.
5. A language-only tenant sync via `TenantCustomerLanguageService` / `SuperAdminTenantMarketService::syncCustomerLanguagesToTenant()`.

The Frontend V2 server derives its supported locale list from the installed UI dictionaries (`supportedUiLocales`). There is no second hard-coded server whitelist to update.

The customer-language sync writes only customer locale configuration such as `pmd_v2_enabled_languages`; it does not re-apply payment, currency, order, reservation, or menu data.

## Admin language pack

A full Admin language additionally requires:

- `app/admin/i18n/platform/<locale>.php` with parity against the canonical English Admin catalogue.

`Admin\Classes\PmdPlatformI18n` discovers installed Admin catalogues dynamically. `scripts/pmd-audit-platform-i18n.php` also discovers them dynamically and fails if a translated Admin catalogue is missing canonical keys or has placeholder mismatches.

A customer language can therefore launch before its Admin catalogue. The Admin remains on a complete supported locale until the full Admin pack is ready.

## Restaurant-created content

Restaurant-created names and descriptions are tenant data, not platform copy. Enabling a locale does **not** machine-translate or overwrite menu items, categories, restaurant names, floor names, staff names, or other tenant-owned content.

When tenant-owned translations exist in the menu/category payload, Frontend V2 already resolves locale-specific `translations`, including Arabic.

## Oman R1

Oman uses:

- default customer language: `en`
- enabled customer languages: `en`, `ar`
- Arabic direction: `rtl`
- Admin Arabic: not exposed until a complete canonical Admin Arabic catalogue is installed

Bulk existing-tenant sync:

```bash
php scripts/pmd-sync-oman-customer-languages-r1.php
php scripts/pmd-sync-oman-customer-languages-r1.php --apply
```

The first command is read-only. The second applies and verifies the language settings for every central-control-plane tenant whose country profile resolves to Oman.

## What “one action” means

Once a language pack exists and the market profile declares it eligible, **activation/synchronization is one action**. The translation content itself is not generated by activation; it must be supplied and reviewed as part of the language pack.
